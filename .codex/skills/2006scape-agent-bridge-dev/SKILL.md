# 2006Scape Agent Bridge Dev

Use this skill for bridge/tool development. Pair it with `2006scape-dev-editing` for general repo edit rules and `2006scape-local-runtime` when live restart or session-claim work is required.

## Boundaries

Other agents may be using the game. Do not restart the server/client, kill processes, or replace running jars while editing bridge code unless the user explicitly asks for runtime validation. Compile-time validation is not live validation.

Keep tools server-authoritative. HTTP handlers must not mutate gameplay directly; queue or execute through `AgentActionService`, which runs against the claimed player and existing game mechanics. The bridge HTTP server is a bounded localhost control plane with request-body limits plus request and game-tick action backpressure, not a public remote API; do not expose the loopback bridge, which defaults to `127.0.0.1:43610`. Remote player-agent access must go through an HTTPS gateway that exposes only approved `/agent/*` endpoints and forwards to loopback. Unexpected bridge tool runtime failures should still return compact JSON with `success:false` instead of escaping as raw HTTP handler failures.

Prefer a primitive-first bridge boundary. New gameplay strategies should usually be Python scripts that compose stable primitives such as `use_item_on_item`, `use_item_on_object`, `click_interface_button`, `select_interface_item`, `interact_object`, `interact_npc`, movement, wait, bank, shop, and combat tools. Add Java only when the bridge is missing a reusable gameplay input primitive; do not add a new bespoke Java tool for each skill loop.

All new or changed bridge primitives must be player/session scoped and profile-neutral. The claimed `AgentSession` player is the authority; do not hard-code a profile, default session files, profile-specific paths, or current-account assumptions into Java metadata, handlers, compact aliases, or result shaping. If a helper script is needed for proof or strategy, it must accept `--profile PROFILE` or honor `RS_PROFILE`/`RSBRIDGE_PROFILE` and pass that profile through to the bridge wrapper.

Never print or copy bridge tokens. Use `agent-navigation/tools/rs-tool_XS.sh` or `agent-navigation/tools/rs-tool_XXS.sh` for routine live proof; use full `agent-navigation/tools/rs-tool.sh` only when a compact alias omits a named field needed to prove or debug the change.

## Main Files

- `2006Scape Server/src/main/java/com/rs2/agent/AgentBridgeServer.java`: local HTTP bridge, health, session claim, and tool endpoint.
- `2006Scape Server/src/main/java/com/rs2/agent/AgentSessionManager.java`: nonce/session ownership and token validation.
- `2006Scape Server/src/main/java/com/rs2/agent/AgentActionService.java`: tick-aware action queue, movement/wait batches, and legacy compatibility batches.
- `2006Scape Server/src/main/java/com/rs2/agent/AgentToolService.java`: immediate primitive handlers, legacy tool handlers, and `observe_state`.
- `2006Scape Server/src/main/java/com/rs2/agent/AgentChatService.java`: bounded structured agent/player chat bus used by compact chat bridge tools and Discord transport.
- `2006Scape Server/src/main/java/com/rs2/integrations/discord/DiscordAgentTransport.java`: optional per-agent Discord bot transport for `AgentChatService`.
- `2006Scape Server/src/main/java/com/rs2/agent/AgentKnowledgeBase.java`: built-in landmarks and static gameplay knowledge.
- `2006Scape Client/src/main/java/CodexAppServerClient.java`: dynamic tool metadata and prompt text exposed to Codex.
- `2006Scape Client/src/main/java/AgentClientController.java` and `AgentBridgeHttpClient.java`: client-side `/agent` control and claim communication.
- `agent-navigation/tools/remote_claim.py`: repo-side remote bridge claim helper that writes profile-scoped ignored sessions with `bridgeUrl`.
- `scripts/render-agent-bridge-gateway-config.py` and `scripts/probe-agent-bridge-gateway.py`: public-safe gateway config and external reachability/non-exposure checks.

## Remote Player-Agent Mode

Local `/agent` behavior uses `http://127.0.0.1:43610` by default. Packaged clients may set `agent.bridge.url=https://AGENT_GATEWAY_HOST` in `client.properties`; `/agent key`, `/agent status`, `/agent stop`, and `/agent <task>` should then claim through that gateway after the player proves ownership over the game connection.

Repo-side Codex control uses:

```sh
python3 agent-navigation/tools/remote_claim.py --profile PROFILE --bridge-url https://AGENT_GATEWAY_HOST --verify
```

The helper prints the in-game `::agent claim CODE` command, consumes the claim through `/agent/session/claim`, and writes the ignored profile session file. `rs-tool.sh`, `rs-tool_XS.sh`, `rs-tool_XXS.sh`, `observe_XS.sh`, and `bridge_script.py` must preserve legacy local sessions while honoring session `bridgeUrl` for remote sessions.

## Tool-Change Checklist

When adding or changing an `rs.*` primitive:

1. Define or update the tool metadata in `CodexAppServerClient.java`.
2. Route the server-side tool name in `AgentToolService` or `AgentActionService`.
3. Use existing mechanics such as `PlayerAssistant.playerWalk`, `CombatAssistant.attackNpc`, `ClickObject`, `NpcActions`, `UseItem`, shops, banking, or dialogue/interface/item handlers.
4. Preserve session scoping: reject offline, disconnected, dead, expired-token, and wrong-player sessions. Multi-profile behavior must be correct by construction, not only for the legacy default profile.
5. Return a useful JSON result with `success`, a concise message, and compact state when it helps the next decision. XS/XXS aliases should preserve the fields agents need to avoid follow-up full observes.
6. Add or update the player-facing terminal display phrase in `AgentToolDisplayText` so the Agent Console shows concise English action text instead of raw `rs.*` names.
7. Add or update focused tests when behavior is shared, risky, has already regressed, could mix up two claimed players, or changes advertised tool coverage.

Prefer external scripts for skill loops. Legacy Java strategy tools such as `mine_ore_until_inventory_full`, `chop_tree_until_inventory_full`, `fletch_logs_until_inventory_empty`, `fish_food`, `cook_food`, `light_fire`, `smelt_bar`, `smith_item`, `plan_smithing`, `train_combat`, `train_smithing_profit`, `equip_best_items`, `combat_cleanup`, `combat_restock_trip`, and `start_combat_goal` are not advertised and are quarantined behind `legacyCompatibility=true` for deliberate stale-runtime compatibility only. Do not add new callers; see `agent-navigation/scripting-primitives.md` for the current boundary.

Prefer batch or wait primitives for long-running actions. `walk_to_tile_until_arrived`, `travel_to_landmark_until_arrived`, `wait_until_idle`, and smart combat waits avoid one-tick polling while keeping strategy in Python. When observing an already-running command from a terminal session, estimate the likely completion interval and wait near that duration instead of polling every few seconds.

Dynamic compact tools are first-class bridge aliases, not separate gameplay mechanics. `*_XS` and `*_XXS` names route through the same server-authoritative handlers and compact the returned payload before it goes back to the model. Keep advertised compact coverage in `CodexAppServerClient.java`, route aliases through `AgentActionService`, and compact through `AgentToolService.compactXsResult` / `AgentToolService.compactXxsResult`. Repo wrappers should hit server aliases directly: `rs-tool_XS.sh TOOL ...` appends `_XS` for known compact-capable tools and `rs-tool_XXS.sh TOOL ...` appends `_XXS`. Current high-use XXS aliases include `observe_state_XXS`, `observe_state_if_changed_XXS`, `combat_state_XXS`, `set_run_XXS`, `walk_path_steps_XXS`, `walk_to_tile_until_arrived_XXS`, `travel_to_landmark_until_arrived_XXS`, `wait_ticks_XXS`, `wait_until_idle_XXS`, `wait_until_combat_event_smart_XXS`, `wait_until_combat_event_XXS`, `object_transition_step_XXS`, `interact_object_XXS`, `click_interface_button_XXS`, `set_combat_style_XXS`, `attack_npc_XXS`, `eat_best_food_XXS`, `pickup_ground_item_XXS`, `bury_bones_XXS`, `deposit_inventory_items_XXS`, `withdraw_bank_items_XXS`, `unequip_items_XXS`, and `food_bank_XXS`. XXS should return only success/message/status/event counters, critical player state (tile, HP/max HP, run energy/enabled, combat, poison, death, free slots, food), and tiny XP deltas. Full tools remain the evidence/debug fallback.

Structured agent/player chat is `AgentChatService` plus `agent_chat_send_XS`, `agent_chat_read_XS`, and `agent_chat_status_XS`. These tools are coordination primitives, not public-gameplay actions: keep them session-scoped to the claimed player, keep results compact, and use `::agentchat message`, `::agentchat @agent:Name message`, `::agentchat @player:Name message`, `::agentchat @all message`, or `::agentchat #channel message` for player-originated client messages. `@all` is a broadcast: it remains visible in the shared agent channel and queues delivery to online game clients. For named bridge targets, prefer `agent:"Name"` or `player:"Name"` alias fields; keep `to` plus `toType` available for generic callers. Target shortcuts are mutually exclusive: use either `agent`/`player` or generic `to` plus `toType`, not both. The service keeps bounded backlog and direct-player delivery queues, and sanitizes message text, names, and channel keys before delivery, optional JSONL logging, or mirroring. `agent_chat_log_enabled=true` writes sanitized envelopes to `data/logs/agent-chat/<yyyy-MM-dd>/agent-chat.jsonl`; do not log bridge tokens or Discord bot tokens. Valid explicit `toType` values are `agent`, `player`, `channel`, and `broadcast`; invalid values must fail closed instead of becoming channel messages. Direct `agent`/`player` targets require a target name, and `deliverToPlayers` is valid only for `player`/`broadcast`. Direct messages are visible to the target, sender name, and sender profile; Discord ingress uses the Discord display name as `fromName` and the configured bot's agent/profile as `fromProfile`. Discord attaches through `DiscordAgentTransport` as a subscriber/publisher to `AgentChatService`; keep at most one `agent-discord-bots` entry per agent/profile, because deployment verification rejects duplicates and the runtime keeps the first usable config if duplicates are accidentally present. Real Discord secrets must not be symlinked or group/world-readable on POSIX systems; runtime loading refuses symlinked secrets and tightens regular secrets files to owner-only before reading. Discord routing filters are optional, but if `allowedAgents` or `allowedPlayers` is present it must be a comma-separated string or JSON array with at least one non-empty name; omit the field for open routing. `allowBroadcast` must be a JSON boolean. The runtime ignores malformed bot configs rather than coercing object allow lists, empty explicit allow lists, non-string fields, or string broadcast flags. Discord mirrored output must escape mentions so game or agent text cannot ping `@everyone`, `@here`, users, or roles. Discord mirror failures must not make in-game chat sends fail, and Discord callbacks must enqueue chat only and must not directly mutate gameplay state or write client packets. Direct player delivery is queued and drained on the server tick; `agent_chat_send_XS` can report `deliveryPending:true`, and if the target player is offline or the client chatbox send fails when drained, later `agent_chat_read_XS` output records the target in `undeliveredTo`.

Trade primitives are player/session-scoped. `request_player_trade_XS`, `offer_trade_item_XS`, `accept_trade_XS`, and `trade_status_XS` must only initiate, offer, or accept from the claimed player; never drive the partner's offer/request state. `request_player_trade_XS` reflects the server's 3-tile player-trade range and may auto-walk a short safe distance toward the target before retrying. `accept_trade_XS` is intentionally a one-call agent accept: it validates optional `expectPartner`, `expectItemId`/`expectItem`, and `minAmount`, accepts the caller's first trade screen, records the caller's auto-final intent, and reports item-count delta when an expected item is supplied. When the other party has also called `accept_trade_XS`, the second confirmation is completed for the two already opted-in sides. Keep explicit `stage`/`screen` handling as a debug fallback only; normal agents should not need to click both human confirmation screens. For receiving-only workflows, use `python3 agent-navigation/tools/receive_trade.py --profile PROFILE --from OTHER_PROFILE --item coins --min-amount N`; it polls compact state and controls only the selected profile.

For repo Python scripts, expose explicit state intent: `bridge_script.observe_xxs()` for confirmation, `bridge_script.observe_xs()`/`bridge_script.observe()` for compact decision state, and `bridge_script.observe_full()` for the rare complete payload. Direct `rs-tool.sh observe_state` is blocked unless `RS_ALLOW_FULL_OBSERVE=1` is set for explicit debug/evidence work. If a compact result lacks a field that forces a full observe, either document that call site or add a reusable compact field/primitive so future scripts do not repeat the full read.

When changing XP-producing tools, preserve the generic progress layer: results should expose `skillChanges` for the current tool call and `xpRecent` for short-lived recent gains. Prayer needs explicit current-point versus base-level wording because bone burial increases XP/base level without refilling current Prayer points.

When updating bank/equipment metadata, expose array fields that already exist server-side. `bank_item_count_XS` is the compact read-only primitive for exact counts of specific banked items by `itemId`, `itemIds`, `name`, `names`, `item`, or mixed `items`; use it instead of full `observe_state` for supply-count questions. `deposit_inventory_items` and `deposit_inventory_items_XS` accept `itemIds` to deposit multiple item types in one call. `withdraw_bank_items_XS` keeps legacy `itemId`/`itemIds`/`name` plus shared `amount` behavior, and supports mixed exact quantities through `items:[{"itemId":440,"amount":9},{"itemId":453,"amount":18}]`; keep that batch summary compact and preserve legacy calls. `unequip_items_XS` accepts `equipmentSlots`, `slotNames`, `itemIds`, `names`/`items`, or `all=true` so agents do not loop one equipment slot at a time.

For external-player network/auth work, read `docs/network-auth-agent-chat-design.md` and `docs/deployment-networking.md` first. Keep local defaults unchanged, keep `AgentBridgeServer` bound to localhost, and treat account auth/Discord transport as opt-in unless external config explicitly enables them. When `external_players_enabled=true`, Java startup requires PBKDF2 account auth enabled, account auto-create disabled, legacy auth fallback disabled, at least 120,000 PBKDF2 iterations, an explicit external transport acknowledgement, and a non-loopback/non-wildcard `public_game_host`. `direct_tcp` must set `require_secure_external_transport=false`, `secure_external_transport_confirmed=false`, and `direct_tcp_external_transport_confirmed=true`; Tailscale/WireGuard/VPN/client TLS tunnel modes require `require_secure_external_transport=true` and `secure_external_transport_confirmed=true`. Java startup also validates typed single-line bind/host/transport config, effective game/cache ports, rejects overlapping listener ports when `file_server=true`, treats HTTP cache bind failure as fatal in external-player mode, rejects wildcard bind hosts unless `wildcard_bind_confirmed=true`, rejects listener arrays that mix wildcard hosts with specific hosts, and keeps `agent_bridge_bind_host` loopback-only with a non-overlapping `agent_bridge_port` defaulting to `43610`. For final deployment evidence, prefer a copied `server-deployment/proof-templates/deployment-proof-manifest.json` with `scripts/deployment-readiness-report.py --proof-manifest PATH` or `scripts/prepare-external-deployment.py --proof-manifest PATH`. The manifest should hold proof paths, markers, usernames, and password environment-variable names only; never put passwords, bridge tokens, Discord tokens, or other secrets in it. Use `scripts/deployment-readiness-report.py --update-proof-manifest PATH` when a successful readiness-report run should write supplied live proof fields into a copied manifest that may still contain unrelated placeholders. Use `scripts/check-deployment-proof-manifest.py PATH --config "2006Scape Server/ServerConfig.json" --secrets "2006Scape Server/data/secrets.json" --require-full-proof --check-files` for a quick structural/full-proof completeness check before running the heavier readiness/prep command. Final-gate manifests must keep `require_full_proof:true` and `require_encrypted_external:true` in the manifest itself so handoff evidence stays self-describing. `prepare-external-deployment.py --require-full-proof` also runs that check early against merged manifest plus CLI values, including proof-file, password-env, encrypted-transport, and `live_reject_login_expected_statuses` presence, before packaging. Unedited placeholder values in the generated template are rejected before proof checks run. CLI flags override manifest fields for one-off reruns.

Readiness/prep reports reject weak proof arguments and inspect the supplied config: direct player chatbox delivery proof uses `--agent-chat-delivery-log-text` plus `--agent-chat-delivery-log-to-name` and must match an `agent_chat_player_delivery` event. When `agent_chat_discord_enabled=true`, missing Discord bot/channel, Discord-to-server, or server-to-Discord proof keeps `deploymentProofStatus` partial. `--agent-chat-log-text` must be paired with `--agent-chat-log-from-type discord --agent-chat-log-from-bot false`, and server-to-Discord proof must not use `--discord-channel-message-allow-human-author`. If Discord routing allow-lists are configured, full Discord readiness also requires `--agent-chat-blocked-log-text BLOCKED_MARKER` or `scripts/verify-agent-chat-log.py --expect-absent` proof that a blocked human/non-bot marker did not enter `AgentChatService`.

For `client_tls_tunnel`, packaged client `server.host` must stay localhost/loopback because the Java client speaks plaintext to a player-side local tunnel. `public_game_host` is the remote TLS endpoint for deployment checks, not the downloadable client's direct socket target. Player-facing packages display `agent-scape` in lowercase and generated launchers use `agent-scape-client.zip`, `agent-scape-client.jar`, `run-agent-scape.command`, and `agent-scape.app`. Packaged launchers try to start the bundled player-side stunnel config automatically when `stunnel` is installed, macOS packages include `run-agent-scape.command` and `Check-Setup.command` double-click wrappers, and the macOS/Linux setup checker can start it temporarily for no-login TCP diagnostics. Generated stunnel configs should keep certificate-chain verification, hostname checking, and `sslVersionMin = TLSv1.2`; live TLS probes should use the same TLS 1.2+ floor. The server-side stunnel accept host is `client_tls_tunnel_server_accept_host` or `public_game_host`, and must be specific, non-loopback, and non-wildcard so it can coexist with the loopback Java listener on the same ports.

## Debugging Pattern

Start with `observe_state_XXS` or `observe_state_XS`, not a mutating action or full observe. Use full `observe_state` only when the compact response lacks a named field needed for the diagnosis. Check whether the failure is:

- metadata missing in `CodexAppServerClient.java`;
- tool name not routed by `AgentToolService` or `AgentActionService`;
- stale running jar after a compile;
- invalid bridge session;
- in-game precondition such as bank not open, no item, wrong interface, no reachable object, combat, death, or insufficient level.

For object, door, gate, floor, and dialogue tools, a `success:true` click is not proof. Verify the post-state proves the transition.
